# خطة تنبيهات محاولات تسجيل الدخول في MIDAD

## ملخص القرار

تُضاف منظومة تنبيه إدارية تسجل وتعرض محاولات المصادقة المهمة فقط. عند نجاح تسجيل الدخول أو رفضه، يظهر تنبيه داخل جرس Back Office يتضمن اسم الحساب إن كان متاحاً، البريد الإلكتروني، نوع النتيجة، ووقت المحاولة. لا تُخزّن كلمات المرور أو رموز OAuth أو رموز الجلسات أو محتوى `state`، وتبقى البيانات متاحة للمسؤول المعتمد فقط.

## 1. نطاق الأحداث

| الحدث | متى يُنشأ التنبيه؟ | الأولوية | البيانات المعروضة |
|---|---|---:|---|
| دخول ناجح | بعد اكتمال OAuth وإنشاء الجلسة بنجاح | عادية | الاسم، البريد، الوقت، النتيجة، معرّف التدقيق |
| محاولة مرفوضة | عندما ينجح التعريف لكن لا يطابق الحساب الإداري المسموح | عالية | الاسم، البريد، الوقت، سبب عام: حساب غير مصرح |
| فشل OAuth | عند رفض `state` أو فشل تبادل الرمز أو انتهاء المحاولة | عالية | البريد إن كان متاحاً، الوقت، نوع الفشل العام، معرّف التدقيق |
| تكرار سريع | محاولات متتابعة من نفس الحساب خلال نافذة قصيرة | لا ينشئ تنبيهاً إضافياً | يُسجل في التدقيق فقط لتقليل الإزعاج |

يجب ألا تُرسل تفاصيل تقنية حساسة إلى واجهة الإدارة. تُعرض أسباب عامة مفهومة، بينما تُحفظ التفاصيل التشغيلية المحدودة في سجل التدقيق وفق سياسة الاحتفاظ.

## 2. شكل التنبيه

يظهر عنوان مثل: «محاولة دخول ناجحة» أو «محاولة دخول مرفوضة». ويحتوي نص التنبيه على الاسم، البريد، والوقت بتوقيت المغرب، مع رابط إلى صفحة سجل التدقيق أو صفحة أمن الإدارة. يُضاف نوع كيان مستقل مثل `auth_login_attempt` حتى لا تختلط هذه السجلات مع الطلبات أو الشكاوى أو التنبيهات التجريبية.

ينبغي الحفاظ على صوت الجرس الحالي، مع تفضيل كتم مستقل لتنبيهات المصادقة حتى يستطيع المسؤول إبقاء أصوات الطلبات مفعلة دون تشغيل صوت لكل محاولة دخول.

## 3. الحماية والخصوصية

تُنشأ التنبيهات من الخادم فقط بعد نقطة الحدث المناسبة، ولا يعتمد النظام على بيانات يرسلها المتصفح لتحديد نتيجة المصادقة. تُحمى القراءة والتصفية والفتح بواسطة `adminProcedure`، ولا تُكشف هذه البيانات في الصفحة العامة أو لأي مستخدم عادي.

لا تُسجل كلمات المرور، رموز الجلسات، رموز OAuth، قيمة `code`، قيمة `state` الخام، أو عناوين URL التي تحتوي على رموز. ويمكن إضافة عنوان IP أو User-Agent لاحقاً فقط بعد قرار صريح، وبصيغة مقيدة ومبررة تنظيمياً، لأنهما بيانات قد تكون شخصية أو حساسة.

## 4. منع التكرار والضوضاء

يُستخدم مفتاح idempotency يتكون من نوع الحدث ومعرّف المحاولة أو نافذة زمنية قصيرة. لا يُنشأ أكثر من تنبيه واحد لنفس النتيجة. أما فشل `state` المتكرر من نفس الجلسة أو المتصفح خلال دقائق قليلة فيُجمع أو يُكتفى بتسجيله في التدقيق، حتى لا يتحول الجرس إلى مصدر تنبيهات مزعجة.

## 5. إعدادات الإدارة

تُضاف مفاتيح مستقلة في إعدادات Back Office:

| الإعداد | القيمة الافتراضية المقترحة |
|---|---|
| تنبيهات الدخول الناجح | مفعلة |
| تنبيهات الدخول المرفوض | مفعلة |
| تنبيهات فشل OAuth | مفعلة مع تجميع التكرارات |
| صوت تنبيهات المصادقة | تابع لإعداد الصوت العام أو مخصص لاحقاً |
| مدة الاحتفاظ بسجل المصادقة | تُحدد قبل التنفيذ وفق سياسة المشروع |

تعديل الإعدادات متاح للمسؤول المصرح فقط، ويُسجل في سجل التدقيق.

## 6. مراحل التنفيذ

### المرحلة الأولى: نموذج البيانات

إضافة نوع تنبيه مصادقة إلى التعريفات المشتركة، ثم إضافة الحقول اللازمة إلى جدول التنبيهات الحالي أو إنشاء سجل تدقيق متخصص إذا احتاجت الأحداث إلى دورة احتفاظ مختلفة. يجب تطبيق migration غير تدميري واختباره قبل الربط.

### المرحلة الثانية: نقطة الربط الخادمية

ربط النجاح بعد اكتمال إنشاء الجلسة، وربط الرفض بعد التحقق من الهوية والصلاحية، وربط فشل OAuth بمسار الفشل الآمن دون تعطيل إعادة التوجيه أو كشف سبب داخلي. يجب عزل فشل إنشاء التنبيه عن عملية تسجيل الدخول نفسها؛ فإذا تعطل التنبيه لا يُرفض تسجيل الدخول الصحيح.

### المرحلة الثالثة: واجهة Back Office

إظهار تنبيهات المصادقة في الجرس وصفحة كل التنبيهات مع فلتر مستقل، وعرض الاسم والبريد والوقت والنتيجة. يُضاف رابط لسجل التدقيق، مع حالات تحميل وفراغ وأخطاء واضحة، واحترام RTL والتجاوب.

### المرحلة الرابعة: الحماية والاحتفاظ

إضافة سياسة حذف أو أرشفة محددة زمنياً، وتسجيل عمليات الحذف الجماعي، والتأكد من عدم ظهور السجلات في استعلامات المستخدمين العاديين أو إحصائيات الطلبات.

### المرحلة الخامسة: الاختبارات والإطلاق

تشغيل اختبارات الصلاحيات، العزل، عدم التكرار، عدم تسجيل الأسرار، فشل مزود التنبيه، العرض الزمني، وسلوك الصوت. ثم فحص TypeScript والبناء والسجلات والتحقق البصري قبل حفظ نسخة منشورة.

## 7. معايير القبول

تُعد الميزة ناجحة عندما يصل تنبيه واحد واضح بعد دخول ناجح، ويصل تنبيه منفصل عند رفض حساب غير مصرح، ولا تُعرض أي كلمات مرور أو رموز أو بيانات جلسة، ولا يستطيع المستخدم العادي قراءة السجل، ولا يتكرر التنبيه بسبب إعادة المحاولة السريعة، وتظل عملية تسجيل الدخول عاملة حتى عند فشل قناة التنبيه.

## 8. قرار البدء المقترح

يُفضّل تنفيذ الميزة على مرحلتين: أولاً تسجيل الدخول الناجح ومحاولات الحساب غير المصرح داخل جرس Back Office، ثم إضافة فشل OAuth بعد التحقق من نقاط الربط الفعلية حتى لا تتداخل معالجة الأخطاء مع حماية OAuth الحالية. لا يُنصح بإرسال البريد أو WhatsApp في المرحلة الأولى؛ يكفي جرس الإدارة وسجل التدقيق إلى أن تُحدد سياسة القنوات والاحتفاظ.
